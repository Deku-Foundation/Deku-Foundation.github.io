Engineering / Roadmap

Progress is a sequence of proofs.

The roadmap follows technical dependencies. A stage advances when its acceptance tests and review evidence exist—not when a calendar date arrives.

Current stage — package and build foundations

The repositories contain architecture proposals and testable prototypes for package metadata, dependency planning, build-plan validation and a non-destructive installer plan. They are not a production package manager, build sandbox, installer or operating-system image.

Stage 1 / Define the contract

  • Agree package schema, architecture/ABI model, version and conflict semantics, file ownership and licence/provenance fields.
  • Define repository trust, signed metadata, key roles, freshness and rollback protection.
  • Specify recipe lifecycle and the boundaries between fetching, sandboxed builds and publication.
  • Keep compatibility imports disabled by default and document rejection rules.

Exit condition: versioned design decisions, fixture corpus, adversarial tests and reviewable threat model.

Stage 2 / Produce verifiable artifacts

  • Implement source acquisition with immutable revisions and digest verification.
  • Build using disposable, unprivileged workers with network disabled after source acquisition, resource limits and isolated outputs.
  • Capture logs, build environment, provenance and test results; compare independent builds for selected packages.
  • Sign repository metadata with dedicated release keys held outside build workers.

Exit condition: repeatable artifact production, signature verification and documented tamper/rollback test results.

Stage 3 / Make package transactions recoverable

  • Install into a temporary root before making host changes possible.
  • Test file manifests, ownership conflicts, symbolic links, path traversal and configuration preservation.
  • Journal transaction states and inject process termination at each transition.
  • Demonstrate idempotent recovery and rollback under low disk space and interrupted updates.

Exit condition: passing install/update/remove/recovery tests with logs and a maintained bootable previous kernel.

Stage 4 / Compose and boot a system

  • Choose a single owner for system-root deployment after a disposable-VM comparison of generation-based and image-based approaches.
  • Pin kernel, toolchain, base userspace, graphics and desktop dependencies.
  • Boot and upgrade in virtual machines; exercise storage, network, graphics, suspend/resume and recovery paths.
  • Keep KDE Plasma as the first desktop profile; evaluate GNOME after the shared base is stable.

Exit condition: clean-install, upgrade, failed-upgrade, recovery and boot smoke tests pass on the supported VM matrix.

Stage 5 / Public preview

  • Publish only real artifacts, with checksums, signatures, source revisions, provenance and known issues.
  • Document system requirements, support scope, upgrade policy, security contact and recovery steps.
  • Record the exact CI and VM results used to approve the release.

Exit condition: release owner signs off on the release checklist and independently verifies the published files.

What is not scheduled yet

There is no promised release date. RPM/DEB import, general-purpose root deployment, hardware claims, GNOME images and a public ISO remain contingent on the relevant security and integration tests.
