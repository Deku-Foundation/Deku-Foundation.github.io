مسار مساهمة قابل للمراجعة

  1. حدد المستودع المناسب. اقرأ README وابحث عن المكون المسؤول، ولا تفتح الطلب نفسه في جميع المستودعات.
  2. اكتب مشكلة محددة. اشرح المشكلة والسلوك المتوقع وخطوات إعادة إنتاجها ومعايير القبول.
  3. أبقِ طلب الدمج مركزًا. اشرح السبب وأضف الاختبارات وحدّث الوثائق واذكر ما لم يُختبر.
  4. انتظر نتائج الفحوص. تحقق من Actions لنسخة طلب الدمج نفسها؛ وجود commit لا يعني التحقق من السلوك.
  5. لا تنشر إلا بأدلة. يجب أن يشير الإصدار إلى وسم وملفات وبصمات وتوقيعات أو إثبات مصدر معروف وقيود معلنة.

يجري فريق الصيانة التغييرات المعتادة مباشرةً على dev، ويشغّل الفحوص المطلوبة ويراجع الفروق. بعد نجاح جميع الفحوص، حدّث main مباشرةً إلى التزام dev الذي اجتازها؛ لا تستخدم طلب دمج لترقية dev إلى main. احتفظ في هذا المستودع بفرعي main وdev فقط. يمكن للمساهمين الخارجيين اقتراح التغييرات من fork لمراجعتها ودمجها في dev. راجع دليل المساهمة وسير العمل الهندسي. للإبلاغ عن ثغرة، اتبع تعليمات الإبلاغ الخاص في SECURITY.md بدلًا من نشر التفاصيل علنًا.

المشكلة تصف خللًا أو تحسينًا محددًا أو سؤالًا معماريًا بنتيجة متوقعة. طلب الدمج يقدم فرق الشيفرة واختباراته وحدوده. حوّل نقاش التصميم الكبير إلى قرار مسجل قبل التنفيذ.

Projects وDiscussions

كانت GitHub Discussions معطلة في المستودعات الأساسية عند التحقق في 23 أكتوبر 2026. استخدم حاليًا المشكلات المحددة للأسئلة والاقتراحات. يمكن للمسؤول تفعيل Discussions من الإعدادات لاحقًا وإنشاء فئات للإعلانات والأسئلة والنقاشات المفتوحة.

الإصدارات واستضافة الحزم

تناسب GitHub Releases الإصدارات المصدرية والملفات الموقعة بعد توفرها. لكنها لا تستبدل بيانات المستودع الموقعة والتحقق من الحداثة والحماية من التراجع المطلوبة لمدير حزم Linux. لا توجد صورة ISO قابلة للتثبيت منشورة حتى الآن.

بوابات الجودة قبل الدمج

  • الشيفرة: اختبارات للسلوك المعدل ومدخلات عدائية ذات صلة.
  • الأمان: لا سكربتات بصلاحيات مرتفعة دون ضوابط، ولا أسرار مكشوفة أو تبعيات غير مراجعة أو تجاوز صامت للثقة.
  • الوثائق: توضح النطاق الحالي وحالات الفشل والقيود.
  • التوافق: توضح المعمارية وABI والتحديث والاستعادة.
  • الإصدار: ترتبط الادعاءات بملفات حقيقية لا بشارات تُحدّث يدويًا.
