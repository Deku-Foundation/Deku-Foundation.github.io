04 / Security

Security is a process, not a badge.

Deku aims to make security properties reviewable through source provenance, least privilege, isolated builds, clear reporting channels, and verifiable releases.

Current security posture

The project is in development. A threat model and security policy are being developed, but the distribution has not undergone a release-level security audit. Do not interpret the goals on this page as proof that an unreleased system is secure.

Do not send credentials, private keys, access tokens, or exploit details in public issues. Use the reporting instructions in the project security policy.

Engineering priorities

  • Source provenance: pin upstream source revisions and verify downloaded source artifacts.
  • Dependency review: review licenses, maintainers, known vulnerabilities, and update paths.
  • Build isolation: reduce ambient host access and record the inputs and logs for builds.
  • Least privilege: separate CI validation, artifact building, signing, and publication permissions.
  • Release integrity: publish checksums and cryptographic signatures only when a real release pipeline exists.
  • Vulnerability handling: provide a clear private reporting path, triage process, and coordinated disclosure policy.

Security policy and threat model

Read the project’s security policy ↗ and threat model ↗. These documents describe intended process and assumptions; they are not an audit certificate.

Report a vulnerability

Use GitHub’s private vulnerability reporting feature for the relevant repository if it is enabled. Otherwise, consult the current security policy for the supported contact route. Avoid filing exploitable details publicly before maintainers can assess the report.

Transparency

Known limitations, release blockers, and material security changes should be documented in public project records when disclosure is safe and appropriate.
