01 / Principles

Good foundations
are not shortcuts.

A distribution is more than a desktop theme or a list of packages. It depends on a dependable way to build software, distribute it, update it and recover when something fails.

01
◎

Make decisions inspectable

Architecture proposals, upstream choices and known limitations belong in version control—not hidden behind launch claims.

Read the engineering notes ↗
02
⌁

Keep trust boundaries narrow

Reviewed inputs, signed repository metadata, isolated builds and least-privilege workflows are foundational requirements.

Explore the security model ↗
03
↻

Prove recovery works

Install, upgrade, rollback, boot and removal must survive repeatable tests before becoming release promises.

02 / The platform

One system.
Clear responsibilities.

Deku keeps recipes, builds, repositories, package planning and installation separate. This lets each component be reviewed and tested on its own terms.

03 / Software compatibility

Meet software where
it can run safely.

The aim is broad access to software—not a misleading promise that every package can be converted without changes. Format, ABI, services and permissions all matter.

DEFAULT TRUST PATH

Native Deku packages

Reviewed recipes, pinned source inputs, declared dependencies and signed repository metadata. This is the intended system-package path.

A
PREFERRED FOR EXTERNAL SOFTWARE

Rebuild from upstream source

Review the source and licence, patch where needed, build for the Deku target and test the resulting native artifact.

B
DESKTOP APPLICATIONS

Flatpak integration

Use the maintained upstream runtime and sandbox model for desktop applications, with origin and permissions visible.

C
ADVANCED · OFF BY DEFAULT

RPM and DEB inspection

Inspect first, never run foreign maintainer scripts by default, and reject packages whose behaviour or dependencies cannot be represented safely.

D
i

Compatibility is tested, not assumed. Containers, AppImages and virtual machines may help with some applications, but they do not replace host drivers, kernel modules or boot-critical services. Read the compatibility strategy.

04 / Roadmap

Milestones tied
to evidence.

The project does not set a release date ahead of its engineering work. Every milestone has a testable exit condition.

  2. 02
    NEXT

  3. 03

  4. 04
    RELEASE GATE

    Bootable system image

    VM install, boot and upgrade tests before any public ISO announcement.
