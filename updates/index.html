Project / Updates

Follow changes at the source.

Deku does not publish an editorial changelog for unreleased builds. Until release artifacts exist, the most reliable record is the commit history, pull requests and automated test results.

Follow component-level changes

Architecture & project direction ↗Architecture decision records, integration notes and technical policies. Package manager ↗Rust package metadata model, digest validation and dependency planning. Build tooling ↗Input validation and safety checks before build execution exists. Installer planning ↗Plan-only storage validation and non-destructive testing. Package recipes ↗Metadata schema, source pins, licence records and validation. Website changes ↗Website source, accessibility and publication checks.

What counts as a release update?

A release announcement should point to an actual versioned artifact and include its publication date, architecture, file size, checksum, signature verification, source revision, release notes and known limitations. There is no official ISO release at this time, so no download or version history is shown here.

Prefer changes you can verify

For each repository, review the change, its tests and any deployment result together. A successful linter is useful evidence for the scope it covers; it is not proof that the full operating system, installer or package ecosystem works in production.
