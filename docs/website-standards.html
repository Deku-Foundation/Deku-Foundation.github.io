Website / Engineering notes

A design system built for clarity, access and long-term maintenance.

The website is part of the project’s engineering surface. It should explain real project status, stay accessible across devices and languages, and remain easy to build and review.

Website standardsHomepageDocumentationCommunityRoadmapSecurity

Technology choice: static first

The production site remains dependency-free HTML, CSS and small progressive-enhancement JavaScript. GitHub Pages can publish the source directly, so a framework build is not a prerequisite for changing content. This avoids an extra supply-chain and build layer while the project’s publication process is still taking shape.

The trade-off is explicit: multilingual pages are authored as static route counterparts, with a small amount of duplicated structure. If the number of locales and pages makes this difficult to maintain, evaluate a generator such as Astro with Starlight before introducing it. A migration should demonstrate simpler translation workflows, tested fallback behaviour and equivalent output—not merely add a modern tool.

Design references and what Deku takes from them

  • GitHub Primer: use a coherent set of colour, spacing, typography and component tokens; keep focus states, controls and link behaviour consistent. The site uses its own green identity and does not copy Primer code or branding. Primer design system ↗
  • Astro i18n and Starlight: use stable language-prefixed routes, equivalent pages across locales, explicit language tags and an RTL setting for Arabic. The current static site follows those routing principles without adopting a build framework. Starlight internationalisation ↗
  • GOV.UK Design System: make navigation, content structure, language labels and common page patterns consistent; state what the user can do next and avoid inflated wording. Deku uses the clarity principles, not a government visual theme. GOV.UK Design System ↗
  • WCAG 2.2: treat keyboard operation, visible focus, contrast, reduced motion, semantic landmarks and meaningful alternative text as implementation requirements. Automated checks help find regressions but do not establish full conformance. WCAG 2.2 ↗

Visual system

  • Evergreen and leaf green identify Deku; neutral paper and white surfaces support long reading. Colour is not the sole way to signal status.
  • Reusable CSS variables define colour, spacing, widths, borders, radius and elevation. Avoid one-off decorative styles without a content or interaction purpose.
  • Use a system-font stack and local SVG marks. Do not add external font requests, tracking pixels, autoplay media or third-party JavaScript just to improve appearance.
  • Use layout that prioritises the message and technical material over simulated metrics, fake testimonials, made-up release cards or generic marketing copy.
  • Respect reduced-motion preferences, support small screens and keep long lines and dense navigation under control.

Language and right-to-left support

English is the default route; French lives under /fr/ and Arabic under /ar/. Each page sets an accurate HTML lang value. Arabic pages set dir="rtl" on the root element and use CSS logical properties for inline and block spacing. Links use visible language names and remain usable without JavaScript.

Equivalent pages should use canonical URLs and language alternates when the translation exists. Keep page structure equivalent, translate user-facing navigation and status text, and do not label untranslated content as translated. Native-language review is still recommended before claiming editorial translation quality.

Content standard: say only what the project can support

Write about shipped behaviour in the present tense only when code and tests support it. Label proposals as proposals, prototypes as prototypes, and missing features as not implemented. Never imply an ISO, security certification, package compatibility, deployment or release date without a verifiable artifact and evidence.

Prefer short, precise statements. Explain the user consequence and the next step. Avoid stock phrases, repeated slogans, invented statistics, unsupported superlatives and generic filler that does not help someone make a decision.

Quality gates

  1. Validate all local links and image targets; reject duplicate IDs and missing document metadata.
  2. Validate supported document languages and require dir="rtl" for Arabic.
  3. Check JavaScript syntax, language switch targets, canonical URLs and sitemap coverage in CI.
  4. Use keyboard-only navigation, visible focus, browser zoom, reduced motion and mobile widths in manual review.
  5. Inspect Arabic shaping, text direction, punctuation, English technical identifiers, code samples and mixed-direction links in a real browser.
  6. Confirm a successful default-branch Pages deployment and inspect the deployed site before calling it live.

The automated workflow is a guard against known regressions, not a claim that every WCAG criterion has been audited. Accessibility and native-language review remain human tasks.

Source and deployment

The public source is Deku-Foundation.github.io ↗. The Pages workflow separates pull-request validation from deployment and gives Pages permissions only to the deploy job. Do not include credentials or deployment secrets in source, logs or pull-request test jobs.
