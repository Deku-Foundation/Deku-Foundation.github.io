Engineering / Architecture

Broad compatibility. Narrow trust.

Deku aims to make a wide range of software usable without pretending every package format, ABI, service model or installer is interchangeable. The design goal is to reuse mature upstream components where they solve a problem well, and build only the integration that makes Deku coherent.

Project status: this page describes a proposed target architecture and evidence-based design choices. It is not a claim that the package manager, immutable store, sandboxed build service, rollback system or installer is production-ready.

Decision summary

  • Native system packages: a Rust package manager and reviewed Deku recipes, backed by signed repository metadata and immutable package artifacts.
  • Builds: a separate build service, pinned source revisions and checksums, unprivileged workers, network-disabled build phases, recorded provenance and reproducible-build work where practical.
  • System updates: immutable package payloads selected through explicit system generations; stage changes before activation and retain a known-good bootable generation.
  • Desktop apps: integrate upstream Flatpak rather than implement a second Flatpak runtime or sandbox.
  • Compatibility imports: disabled by default. Inspect RPM/DEB archives without running maintainer scripts; prefer rebuilding from source or using Flatpak.
  • Desktop: KDE Plasma first. Keep desktop integration modular so GNOME can be added without changing package trust or transaction semantics.
  • Kernel: track stable releases for supported images; test mainline builds separately. A newer version number is not a substitute for boot, driver, update and recovery tests.

What to learn from established projects

Nix: immutable store and generations

Nix demonstrates the value of keeping package payloads in versioned store paths and switching user or system profiles between known states. Deku should adopt immutable payloads, explicit generations and rollback semantics, but not copy Nix evaluation or derivation semantics wholesale. The store needs a defined garbage-collection policy, disk-space preflight, profile ownership and protection against deleting live references. Nix itself documents sandboxed builds and its store model in its manual.

Fedora: mature package workflows and image-based deployment

Fedora offers two useful lessons: conventional RPM-based package management has a large ecosystem, while rpm-ostree and bootc explore image-based, staged operating-system updates. Deku should not recreate DNF, RPM or OCI image machinery without a compelling interoperability requirement. The practical lesson is to stage changes, verify the next bootable state, keep recovery paths, and separate OS lifecycle from desktop application delivery. See the Fedora documentation and bootc project.

Void Linux: explicit packages and a separate build tool

Void's XBPS and xbps-src illustrate the value of separating binary package installation from package building, keeping package metadata explicit, and testing builds in constrained environments. Deku should preserve that separation: the client must not become a privileged build executor, and recipe review must remain distinct from repository publication. See the Void handbook.

Flatpak: application sandboxing and runtimes

Flatpak is the preferred compatibility route for many third-party desktop applications because it already has a runtime model, application permissions and integration with Flathub. Deku should call the upstream tools and expose origin, permissions and update state clearly. Flatpak does not replace the native package manager for kernels, drivers, host services or system libraries. Read the Flatpak documentation before defining the integration contract.

Store, activation and recovery

Proposed layout: immutable payloads under /deku/store/<content-id>, selectable system profiles under /deku/profiles/system/<generation>, mutable machine state under /deku/var, and administrator-managed configuration under /etc. User data remains in normal home directories and XDG locations.

  • Package payloads are content-identified and never overwritten in place.
  • A transaction resolves dependencies, verifies signatures and digests, checks free space, downloads to a staging area, validates every artifact, and prepares a new generation before activation.
  • Activation must be atomic at the profile/boot-selection boundary. If staging fails, the active generation remains unchanged.
  • Keep at least one previous known-good generation, but define bounded retention and safe garbage collection of unreferenced store objects.
  • Do not treat a symlink switch alone as complete integration. ELF interpreters, RPATH, plugin discovery, desktop files, icons, D-Bus services, systemd units, udev rules, initramfs generation and kernel modules need explicit handling and tests.
  • Keep machine configuration and mutable application data out of immutable package payloads. Migrations must be explicit and have failure behavior.

A compatibility policy that does not overpromise

1. Official Deku packagesDefault trusted route for system components. Reviewed recipes, pinned inputs, explicit dependencies, signed repository snapshots and a supported update policy.
2. Rebuild from sourcePreferred for unsupported software when the license and source permit it. Review patches, build in isolation, record provenance and test on Deku.
3. Flatpak / FlathubPreferred for many desktop applications. Use upstream sandbox and runtime tooling; show application permissions and origin to the user.
4. RPM / DEB import (advanced)Off by default. Inspect archive metadata and file paths without executing scripts. Reject unsupported maintainer hooks, file conflicts, privileged service setup and incompatible dependencies. Never run imported install/remove scripts as root.

“Supports everything” should mean a documented route for evaluating and running different software—not a promise that every binary package installs unchanged. CPU architecture, libc and ABI, kernel interfaces, filesystem layout, service managers, graphics stacks, licenses and application assumptions all affect compatibility.

Security boundaries and threat model

  • Repository trust: verify signed metadata, key identity, expiry/freshness and rollback protection. Separate repository signing keys from build workers and website deployment credentials; document key rotation and revocation.
  • Artifact integrity: a checksum detects byte changes but does not establish who published the bytes. Verify both the signed metadata chain and the artifact digest.
  • Build isolation: unprivileged, disposable workers; restricted mounts and namespaces; deny network access during build steps unless a separately reviewed fetch phase is required. Apply seccomp and Landlock where supported, with defense in depth rather than treating one sandbox feature as a complete boundary.
  • Archive extraction: reject absolute paths, traversal, unsafe links, duplicate/conflicting paths, device nodes and unexpected ownership/capability metadata. Bound archive size, expanded size, file count and nesting.
  • Transactions: do not run arbitrary package scripts as root. Define narrowly typed integration actions, validate their inputs, log them, and test rollback after failures at every phase.
  • Supply chain: pin source revisions, verify checksums, record licenses and provenance, review patches, minimize build-time dependencies and publish reproducible-build comparisons when achievable.
  • Operations: protect CI with least-privilege permissions and immutable action pins. Security reports need a private disclosure route before a public release is announced.

Release gates: evidence before claims

  1. Metadata parser and dependency solver: fuzzing, property tests, deterministic plans and malformed-input tests.
  2. Repository trust: signature verification, expired metadata, revoked keys, stale snapshots and rollback attacks tested with fixtures.
  3. Archive handling: hostile archives, path traversal, links, size bombs and conflicting files tested in an unprivileged temporary root.
  4. Transactions: interruption at every stage, disk-full handling, recovery, idempotence and preservation of the active generation.
  5. Boot and kernel: install/update/revert cycles on virtual machines and representative hardware; Secure Boot policy and kernel-module compatibility documented.
  6. Desktop integration: app launch, updates, permissions, portals, D-Bus, icons, fonts, locale, accessibility and multi-user behavior tested.
  7. Release candidate: clean install, upgrade from previous image, offline recovery, signed artifacts, SBOM/provenance, documented known issues and tested restore procedures.

Kernel policy is release-specific. Consult kernel.org and select a supported stable kernel that has passed Deku's test matrix. Mainline kernels can be evaluated in a clearly labelled experimental channel with a fallback kernel and no implication of production support.
