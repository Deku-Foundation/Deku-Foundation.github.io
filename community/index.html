Community / Participation

Build in the open.
Make the work reviewable.

Deku is an early-stage engineering project. The best contributions make a specific improvement, explain why it matters, and include evidence that someone else can check.

Choose a useful starting point

Report a problem or propose work ↗Describe the observed behaviour, expected outcome, environment and evidence. Search existing issues first. Read the contribution guide ↗Review the project workflow, licensing expectations and standards for focused changes. Review architecture proposals ↗Check the reasons, alternatives, security assumptions and unresolved decisions behind the platform. Help with package metadata ↗Source pins, licence records, dependency declarations and schema validation need careful review.

What a useful contribution looks like

  • It addresses one problem and states its scope clearly.
  • It separates current behaviour from a proposal or assumption.
  • It adds or updates tests, documentation or reproducible evidence where appropriate.
  • It records upstream source, licence obligations and patch rationale when upstream software is involved.
  • It avoids credentials, private data, generated binaries and unrelated refactoring.

Before opening a large change

For changes that affect package trust, system layout, update behaviour, boot recovery or the project’s upstream choices, start with an issue or architecture decision proposal. A smaller experiment can reveal costs and failure modes before the project commits to a design.

Review and conduct

Review should focus on correctness, security boundaries, maintainability and evidence—not the size of a change. Participation is subject to the project’s Code of Conduct ↗ and contribution guidelines ↗.

Where the community meets today

Public work currently happens in GitHub issues, pull requests, commits and repository documentation. A separate forum or real-time chat is not listed as an official project channel at this time. Use the project repositories so discussions remain findable and connected to the code.

Security concerns

Do not publish exploitable details, credentials or private keys in a public issue. Follow the project’s security policy ↗ and use a private reporting route where available.
