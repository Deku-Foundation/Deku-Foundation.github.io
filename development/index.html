A contribution path that stays reviewable

  1. Find the owner. Read the repository README and locate the component responsible for the behaviour. Do not open the same request in every repository.
  2. Use an issue for scoped work. Include a problem statement, observed behaviour, expected outcome, reproduction steps where applicable, and testable acceptance criteria.
  3. Keep each pull request focused. Explain why the change is needed, identify compatibility or security effects, add tests, update relevant docs and state what was not tested.
  4. Let the checks finish. Review the Actions result for the PR head. Do not describe a change as verified just because the code was committed.
  5. Release only from evidence. A release announcement should link to a version tag, artifacts, checksums, signature/provenance data and known limitations. Those do not exist for an installable ISO yet.

Use dev as the shared integration branch: test and review there, then open a pull request from dev to main only when the checks pass. Keep long-lived branches to those two; temporary branches are exceptions for active pull requests. Read the contribution guide and engineering workflow. For vulnerabilities, follow the private reporting instructions in SECURITY.md.

Use GitHub features for distinct jobs

Issues and pull requests

Issues capture a specific bug, scoped enhancement or architectural question with an expected outcome. Pull requests propose a diff, its tests and its limitations. Use review comments to discuss code; convert a larger design discussion into a tracked decision before implementation.

Actions and commit history

Actions is the live source for workflow results. Commit history shows when and where a change landed. Subscribe to individual repositories for notifications, or use these Atom feeds to follow changes without polling a webpage:

  • Build tooling commit feed

Projects and Discussions

Maintainers configuring these features should follow the GitHub workspace operations runbook ↗.

A shared organization-level project board has not been verified. Until maintainers configure one with repository automation and agreed status fields, use the published roadmap and repository issues as the visible planning record.

GitHub Discussions was disabled on the core repositories when checked on 23 October 2026. For now, use focused issues for actionable questions and proposals. A maintainer can enable Discussions in repository settings later and create categories for announcements, Q&A and open design conversations; do not rely on a discussion URL until that setting is enabled.

Releases and package hosting

GitHub Releases are appropriate for versioned source releases and signed, testable artifacts when they exist. They are not a substitute for the signed repository metadata, freshness controls and rollback protection required by a Linux package repository. Do not treat the absence of releases as an invitation to publish placeholder downloads.

Quality gates before merge

  • Code: tests cover changed behaviour and adversarial input, where applicable.
  • Security: no new privileged scripts, unreviewed dependencies, exposed credentials or silent trust bypasses.
  • Documentation: current status, failure modes and supported scope are stated accurately.
  • Compatibility: architecture, ABI, update and recovery implications are explicit.
  • Release claims: CI, images, packages and signatures are linked to real artifacts rather than manually maintained badges.
