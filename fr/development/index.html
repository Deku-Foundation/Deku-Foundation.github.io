Un parcours de contribution vérifiable

  1. Trouver le bon dépôt. Consultez le README et repérez le composant responsable. N’ouvrez pas la même demande partout.
  2. Créer un ticket précis. Décrivez le problème, le résultat attendu, les étapes de reproduction et les critères d’acceptation.
  3. Limiter la pull request. Expliquez le besoin, ajoutez les tests, mettez à jour la documentation et mentionnez ce qui n’a pas été testé.
  4. Attendre les contrôles. Vérifiez le résultat Actions correspondant à la tête de la pull request. Un commit ne signifie pas qu’un comportement a été vérifié.
  5. Ne publier qu’avec des preuves. Une version doit référencer son tag, ses artefacts, sommes de contrôle, signatures/provenance et ses limites connues.

Utilisez dev comme branche d’intégration partagée : testez et révisez les changements, puis ouvrez une pull request de dev vers main seulement lorsque les contrôles passent. Limitez les branches durables à ces deux noms ; les branches temporaires restent des exceptions pour une pull request active. Consultez le guide de contribution et le flux d’ingénierie. Pour une vulnérabilité, suivez la politique privée dans SECURITY.md.

Tickets et pull requests

Un ticket décrit un problème concret, une amélioration délimitée ou une question d’architecture avec un résultat attendu. Une pull request propose un diff, ses tests et ses limites. Transformez les grandes discussions de conception en décision suivie avant l’implémentation.

Versions et hébergement de paquets

GitHub Releases convient aux sources versionnées et aux artefacts signés lorsqu’ils existeront. Ce n’est pas un remplacement des métadonnées de dépôt signées, des contrôles de fraîcheur et de la protection contre les retours arrière nécessaires à un gestionnaire de paquets Linux. Aucune image ISO installable n’est publiée.

Critères qualité avant fusion

  • Code : tests couvrant le comportement modifié et les entrées hostiles pertinentes.
  • Sécurité : aucun script privilégié ajouté sans contrôle, secret exposé, dépendance non examinée ou contournement silencieux de confiance.
  • Documentation : portée actuelle, échecs et limites décrits sans ambiguïté.
  • Compatibilité : architecture, ABI, mises à jour et récupération explicités.
  • Publication : les annonces renvoient à des artefacts réels, pas à des badges entretenus manuellement.
